# Phase 06 — Architecture, ImplementationSpec, Task Planning and TaskContract Compiler

## 1. Objective

Turn approved FeatureSpecs into bounded, executable engineering work. This phase introduces:

- the project-level **Architecture** (versioned, approved, with Contracts and Decisions), proposed by **Atlas** via a live LLM;
- feature-level **ImplementationSpec** versions, generated by **Kira** (live) and validated **against** the Architecture;
- Kira's live **TaskPlan**, validated deterministically (DAG acyclicity, references, scope, AC coverage) and persisted as Tasks;
- the deterministic **TaskContract compiler**, which produces immutable contracts.

It also wires the Greenfield **repository precondition**. The `GREENFIELD_MANAGED` Repository is declared when the cycle is created (Phase 01) and provisioned by Phase 04's `RepositoryMaterializationService` (bare repository plus baseline commit, revision #1). Phase 06 relies on the Phase 01 guard `repository_ready_with_canonical_commit` on `start_planning`, which pins `delivery_cycles.base_sha` to the baseline SHA, so planning and every implementation Execution run against a materialized canonical RepositoryWorkspace. The phase also adds the guard that **CODE_CHANGE tasks must trace to an approved ImplementationSpec** (TECH T2→T3 boundary). Generated code reaches the project only as Git commits (README §5.9.1).

## 2. Architectural Context

- **Position:** Work plane (planning) plus the Architecture/ImplementationSpec layer of the product model. Greenfield ARCHITECTURE → PLANNING → DEVELOPMENT.
- **Upstream:** 05 (approved FeatureSpecs, ACs), 04 (tool catalog, `git_local`), 03 (executions), 01 (approvals, guards).
- **Downstream:** 08 (lineage Task → ImplementationSpec), 09 (Warden checks architecture/ImplementationSpec conformance), 10 (Greenfield E2E), 13/14 (ImplementationSpec delta, architecture delta), 15 (REPAIR ImplementationSpec), 12 (REMEDIATION ImplementationSpec).
- **Invariants:**
  - 2–4: ImplementationSpec realizes behavior, Architecture is project-level, and Architecture constrains ImplementationSpec.
  - 5–6: Task is planned work; TaskContract is versioned/immutable.
  - 12: the deterministic compiler. No LLM in contract compilation.
  - "Tasks must trace to an approved ImplementationSpec" (ARCH §4.2).

## 4. Scope

1. Tables: `architectures`, `architecture_contracts`, `implementation_specs`, `task_plans`, `task_spec_refs`. Add `tasks.implementation_spec_id`.
2. **Atlas** (`atlas.propose_architecture`):
   - live LLM;
   - input: approved FeatureSpecs plus NFR requirements plus the existing architecture (none for Greenfield);
   - output `ArchitectureProposal` (components, layers, technology stack, directory conventions, API/data contracts, decisions, constraints, risks).
   The proposal is validated, then persisted as Architecture v1 PROPOSED, then gets Approval(ARCHITECTURE), then becomes APPROVED and immutable.
3. Greenfield repository precondition (README §5.9.3–5.9.4):
   - The `GREENFIELD_MANAGED` Repository and its canonical RepositoryWorkspace are declared at cycle creation (Phase 01). They are provisioned asynchronously by Phase 04 (`git init --bare`, baseline commit `README.md`/`.gitignore`/`OLYMPUS.md`, `registered_sha = canonical_commit =` baseline, revision #1 `MATERIALIZED`), usually long before ARCHITECTURE is approved.
   - `start_planning` is guarded by `architecture_approved` **and** `repository_ready_with_canonical_commit`. Its `pin_base_sha` effect sets `delivery_cycle.base_sha := canonical_commit`. If provisioning failed, `start_planning` returns 422 `REPOSITORY_NOT_READY:ERROR` and the operator uses `retry_materialization`.
   - TaskContracts compiled here use `base_policy=CYCLE_BASE` (no dependencies) or `DEPENDENCY_INTEGRATION`, so every Greenfield implementation Execution starts from the recorded canonical SHA inside its own ExecutionWorkspace. Kira's repository listing input is read from Git at `base_sha` (the baseline files), not from a working tree.
   - Generated code is never persisted as control-plane state. It exists only as candidate commits in ExecutionWorkspaces, and later as IC/canonical revisions in the canonical RepositoryWorkspace (Phase 08).
4. **Kira ImplementationSpec** (`kira.implementation_spec`):
   - live;
   - input: one approved FeatureSpec (+ACs) plus the approved Architecture and its contracts;
   - output `ImplementationSpecDraft` (components, apis, schemas, data_changes, integration_points, required_tests, file_scope, architecture_refs, ac_coverage).
   A deterministic **architecture conformance validator** checks it: every component, API, schema and file scope must map to an Architecture component, contract or directory convention. Otherwise the result is `ARCHITECTURE_DELTA_REQUIRED` and the draft is rejected with a reason. ImplementationSpec does not silently redefine architecture.
5. ImplementationSpec approval (Approval(IMPLEMENTATION_SPEC), per policy).
6. **Kira TaskPlan** (`kira.task_plan`):
   - live;
   - input: approved ImplementationSpecs, Architecture, AC list and repository listing (empty for Greenfield beyond scaffold);
   - output `TaskPlan` (TECH §8.1).
   A deterministic TaskPlan validator checks it, then it is persisted as Tasks (DRAFT) plus dependencies plus `task_spec_refs`.
7. **TaskContract compiler** (deterministic, `core/planning/compiler.py`):
   - input: Task, ImplementationSpec version, FeatureSpec+AC versions, Architecture version + constraints, policy version, tool catalog, plus optional code context selection (Phase 08 adds index-based context);
   - output: `TaskContractBody`, with `compiler_inputs_hash`.
   Then issue the contract and run `mark_ready`.
8. The issue-time guard: CODE_CHANGE with origin IMPLEMENTATION_PLAN/REMEDIATION/REPAIR requires an APPROVED ImplementationSpec and `compiled_by` starting with `compiler:`.
9. Guards: `architecture_approved`, `implementation_specs_approved` (every in-scope FeatureSpec has an APPROVED ImplementationSpec) and `task_plan_accepted_contracts_issued` (latest TaskPlan ACCEPTED; every plan task has an ISSUED contract; mandatory AC coverage complete).
10. RefResolvers for ARCHITECTURE and IMPLEMENTATION_SPEC. The snapshot builder includes `architecture_versions` and `implementation_spec_versions`.

## 5. Out of Scope

- Architecture **delta** for feature changes (14; the schema supports `kind=DELTA` now).
- REPAIR/REMEDIATION ImplementationSpecs (15/12/09; the enum values exist now).
- Code-index-based context selection in contracts (08).
- Executing the planned tasks end to end (10).

### Do Not Change
- The compiler must be pure and deterministic: the same inputs give the same `content_hash`. No model calls.
- Atlas and Kira outputs never become APPROVED without Approval when policy requires it.

```python
class TaskDraft(BaseModel):
    ref: str
    title: str
    objective: str
    work_type: Literal["CODE_CHANGE"]
    implementation_spec_ref: str  # lineage key of an APPROVED ImplementationSpec in context
    ac_refs: list[str]
    requirement_refs: list[str] = []
    allowed_scope: list[str]
    constraints: list[str] = []
    required_outputs: list[str]
    verification_requirements: list[str]
    estimated_size: Literal["S", "M", "L"]


class DependencyDraft(BaseModel):
    task_ref: str
    depends_on_ref: str
    reason: str


class RiskObservation(BaseModel):
    description: str
    severity: Literal["LOW", "MEDIUM", "HIGH"]
    related_refs: list[str] = []


class TaskPlan(BaseModel):
    model_config = ConfigDict(extra="forbid")
    tasks: list[TaskDraft]
    dependencies: list[DependencyDraft]
    risks: list[RiskObservation]
    open_questions: list[Clarification]
```

TaskPlan validator rules:
- Refs are unique and resolvable.
- The graph is acyclic (Kahn).
- `allowed_scope` ⊆ the referenced ImplementationSpec's `file_scope` (glob containment by enumerated-pattern check).
- Every mandatory AC of every in-scope FeatureSpec appears in ≥1 task's `ac_refs`.
- `required_outputs` ⊇ {`candidate_commit`, `changed_files`, `test_results`}.
- `verification_requirements` is non-empty.
- Max tasks per plan comes from policy (default 12).
- Any blocking open question means the plan is not accepted until it is answered.

Compiler output mapping:

| TaskContractBody field | Source |
|---|---|
| `objective` | TaskDraft.objective |
| `inputs` | ImplementationSpec version, FeatureSpec version, AC versions, Architecture version |
| `repository_id`, `base_policy` | cycle repository; `CYCLE_BASE` if no deps else `DEPENDENCY_INTEGRATION` |
| `allowed_scope` | TaskDraft.allowed_scope ∩ ImplementationSpec.file_scope |
| `constraints` | Architecture.constraints + dependency_rules + TaskDraft.constraints + FeatureSpec rules |
| `prohibited_operations` | policy defaults (`modify_ci_config`, `write_protected_refs`, `modify_auth` unless in scope) |
| `allowed_actions` | `AgentProfile("forge").allowed_tools` ∩ policy for work type |
| `required_outputs`, `verification_requirements` | TaskDraft |
| `escalation_rules` | policy: `architecture_change: REQUIRE_APPROVAL`, `ambiguous_requirement: ASK_HUMAN` |

| `timeouts`, `budgets` | policy by `estimated_size` |

## 7. State / Lifecycle Changes

- Architecture: DRAFT → PROPOSED → APPROVED → SUPERSEDED (REJECTED on rejection). Owner `ArchitectureService`.
- ImplementationSpec: DRAFT → PROPOSED → APPROVED → SUPERSEDED / REJECTED. A conformance failure is never PROPOSED (it is stored as a rejected draft artifact with its report). Owner `ImplementationSpecService`.
- TaskPlan: PROPOSED → ACCEPTED (validator pass + no blocking questions + optional HUMAN acceptance if policy `task_plan_requires_approval`, default false) → SUPERSEDED.
- DeliveryCycle GREENFIELD:
  - ARCHITECTURE → PLANNING (`start_planning`): guards `architecture_approved` and `repository_ready_with_canonical_commit` (01); effect `pin_base_sha` (01).
  - PLANNING → DEVELOPMENT (`start_development`): guards `implementation_specs_approved`, `task_plan_accepted_contracts_issued`.
- Task: DRAFT → (compile + issue) → READY/BLOCKED (Phase 01 `mark_ready`).

## 12. Testing Strategy

### Unit Tests
- Compiler determinism: the same inputs give an identical `content_hash`; changing any input changes the hash; the output always passes `TaskContractBody` validation.
- Compiler scope intersection and the constraints merge.
- Conformance validator: unknown component, path outside conventions and unknown contract are rejected. A conformant draft passes.
- TaskPlan validator: cycle, missing AC coverage, scope outside `file_scope`, unknown spec ref and too many tasks.

### Persistence Tests
- APPROVED Architecture/ImplementationSpec immutability.
- TaskPlan acceptance atomicity (failure injection gives no partial Tasks).
- Issuing a manual CODE_CHANGE contract for an IMPLEMENTATION_PLAN task is rejected.

### Integration Tests
- `start_planning` with the declared repository still PROVISIONING (materialization loop paused) → 422 `REPOSITORY_NOT_READY:PROVISIONING`. After the loop provisions it, `start_planning` returns 200, `cycle.base_sha == repository.registered_sha == canonical_commit`, and `repository.materialized` plus SYSTEM-actor ActionRequests for `init_repository` exist. Replaying `start_planning` does not create a second repository or revision.
- Guards for `start_planning` and `start_development` fail and succeed appropriately.

### Runtime / Live-LLM Tests
- The three live tests in §11.
- The refactored Phase 04 live Forge test runs against a compiled contract.

### Workflow Tests (live)
- From an approved SupportDesk scope (created by running the Phase 05 live flow in the fixture), propose architecture → approve → `start_planning` (repository already provisioned by Phase 04; `base_sha` pinned) → ImplementationSpecs → approve → TaskPlan → accept. Then all tasks have ISSUED compiled contracts whose snapshots resolve `base_commit == cycle.base_sha`, and the cycle reaches DEVELOPMENT.

## 14. Acceptance Criteria

- [ ] Architecture and ImplementationSpec are distinct, versioned entities. APPROVED versions are immutable.
- [ ] An ImplementationSpec that references components, paths or contracts not in the Architecture is rejected as `ARCHITECTURE_DELTA_REQUIRED`.
- [ ] An invalid or cyclic TaskPlan is rejected before any Task becomes READY.
- [ ] Every mandatory AC of every in-scope FeatureSpec is covered by ≥1 Task.
- [ ] Every CODE_CHANGE Task references an APPROVED ImplementationSpec, and manual issue of such contracts is rejected.
- [ ] Compiler output is deterministic (identical hash for identical inputs) and involves no model call.
- [ ] Greenfield `start_planning` is rejected until the `GREENFIELD_MANAGED` repository is READY with its recorded baseline SHA. On success, `delivery_cycles.base_sha` is pinned to that canonical SHA, and the repository's provisioning ActionRequests are audited SYSTEM actions.
- [ ] Atlas, Kira ImplementationSpec and Kira TaskPlan run through the live ModelRouter path.
- [ ] Snapshots of planned tasks include Architecture and ImplementationSpec versions.

## 17. Risks / Implementation Notes

- **Glob containment** is undecidable in general. Restrict `file_scope`/`allowed_scope` to prefix-style globs (`dir/**`, `dir/*.py`, exact paths) and validate by prefix comparison. Reject other forms.
- **Model risk:** Kira may produce too-fine or too-coarse tasks. The policy max and human review of the DAG (optional approval flag) mitigate this.
- **Architecture drift risk:** never "auto-fix" conformance failures by widening the architecture. That requires an Atlas delta and approval (14).
- **Deferred:** code-context selection in contracts (08).
